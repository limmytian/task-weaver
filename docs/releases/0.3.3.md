# Task Weaver 0.3.3

Changes from [v0.3.2](https://github.com/limmytian/task-weaver/releases/tag/v0.3.2).
This document describes the prepared source. Release artifacts and deployment
approval are separate gates; existing published images do not acquire these changes.
[简体中文](0.3.3.zh-CN.md).

## Highlights

- Closed local accounts with administrator provisioning, one-time activation and
  recovery, revocable browser sessions, and stable human/managed Agent identities.
- Subject-bound scoped API Keys with rotation, explicit expiry or an explicit
  no-time-expiry choice, live revocation and credential ancestry checks.
- Shared authentication across REST, tRPC, GraphQL, SSR and SSE. Project roles,
  personal ownership and scoped retrieval apply to content, nested links, history,
  files, graphs, MCP, repository metadata, webhooks and execution bookkeeping.
- Authenticated daemon supervision and assigned project Ti execution use explicit
  phase grants, isolated child credentials and task capabilities capped at 15
  minutes and the live parent/lease. Existing review identity and fence rules apply.
- Account, membership, Agent and Key management UI, session/cache isolation, and
  verified CLI login/logout/whoami.
- Approved Open weave identity with indigo/blue palette, accessible light/dark
  tokens, logo masters, favicon, Web/login/CLI and repository assets.
- Dependency security updates, including Next.js 16.3.8, and exclusion of optional
  database schema generation tools from the API runtime, plus authentication,
  cross-actor, execution and upgrade regressions.

## Compatibility and required upgrade work

This patch intentionally replaces the legacy trust model. Integrations relying on
anonymous business access, caller-declared actor headers, old unbound Keys or
implicit administrator access must change. Actor headers, client/node IDs and
legacy labels provide no authority. Instance administrators do not inherit project
membership or another human's personal data. Project visibility does not grant
execution, review, merge or MCP invocation. Human Key-created personal content
belongs to the human; managed Agents retain independent execution attribution.

REST/tRPC/GraphQL callers need verified credentials; browser mutations additionally
need exact Origin and signed CSRF. API Keys are not browser sessions. Missing,
expired or revoked credentials fail closed. No setting restores legacy access.
See [authenticated access](../authenticated-access.md) and
[authentication configuration](../authentication-contract.md).

The migration journal advances from 48 entries through `0047_ti_agent_overhaul`
to 59 through `0058_auth_migration_receipts`. Schema migration alone establishes
neither trusted ownership nor membership. Before opening an upgraded instance:

1. Rehearse on a sanitized copy. Stop API/Web writers and all runners. Verify a
   complete database backup with extension definitions and matching skill storage;
   retain old code/image/configuration references and record the UTC cutoff.
2. Apply forward migrations. Configure API/Web with the same database,
   `TW_AUTH_SECRET`, `TW_AUTH_BASE_URL` and exact `TW_AUTH_TRUSTED_ORIGINS`;
   use HTTPS outside loopback and a single browser origin/reverse proxy. Inject
   these values explicitly via deployment Secrets: a host `.env` alone does not
   inject arbitrary auth variables into the existing Compose/Kubernetes templates.
3. Bootstrap the first human administrator using the one-time deployment
   `TW_AUTH_BOOTSTRAP_SECRET`, then remove it. Provision/activate other humans and
   managed Agents. There is no public signup or inferred identity from old labels.
4. Use the offline ownership tool to inventory the fixed cutoff, review explicit
   resource-to-actor mappings and project memberships, dry-run the manifest, then
   apply with the current fingerprint and maintenance acknowledgement. Supply
   `TW_AUTH_MIGRATION_DATABASE_URL` through the operator's Secret facility.
5. Reissue bounded credentials. Cutover revokes old Keys, clears claims, fences
   delegations/runs, pauses daemons and invalidates provider/repository/embedding
   readiness. Revalidate integrations and explicitly re-register authenticated
   clients. Any later authorized execution requires fresh leases and fences.
6. Verify cross-user/project/personal isolation, login, credential expiry/revocation
   and storage before reopening writers. Unmapped non-project data remains
   quarantined; historical audit attribution is preserved.

The exact tool commands, manifest and recovery semantics are in
[offline upgrade and recovery](../authenticated-access.md#offline-upgrade-and-recovery).
Do not infer ownership from a shared legacy Key, email, label or UUID string.

## Limits and recovery boundary

SLO, assistant/plans entry points, due/background acquisition, unconverted
embedding and assistant/Partners outbound workers, cross-identity local MCP node
sharing, and personal autonomous Ti remain closed. Saved schedules/policies or authorized
streams do not activate workers. Public signup, OIDC/enterprise SSO, MFA, SaaS
multi-tenancy and a custom policy engine are outside this release scope.

Expired/revoked execution cannot resume under old run IDs, tokens or fences.
Reconciliation needs current authorization; dirty changes are retained, while
conflicted/missing workspaces require quarantine and review. No automatic runner
restart is implied by migration or registration.

Prefer forward repair after cutover. Full rollback requires stopping new writers
and restoring the complete pre-upgrade database and matching storage/code/config;
post-backup writes are lost. Never connect 0.3.2 binaries to the mutated 0.3.3 live
database. A schema-only dump or image switch is insufficient. See
[upgrade and recovery](../ce-upgrades.md).
