# Task Weaver 0.3.11

## MCP planning and contextual collaboration

The inbound MCP Server adds 14 tools for skill discovery, safe skill-package
text reads, execution-slice planning, atomic plan submission and bounded task
or requirement context. The catalog contains 43 tools, including 23 available
in read-only mode. HTTP and stdio share schemas and the authorized executor.

Plans support mutation-free previews and persistent credential/project-scoped
UUID idempotency keys. Identical retries return the committed receipt;
conflicting payloads fail. Nested privileged fields and cross-project references
are rejected. Slice updates check the exact current updatedAt and respect
requirement leases. Context reads expose truncation, continuation and honest
read-committed freshness, without recursive document bodies or arbitrary paths.

## Planned MCP authorization follow-up

The next 0.3.11 increment is planned to make the MCP catalog reflect the
authenticated credential's current grants. Discovery must filter tools by their
required permissions, server state and read-only policy; invocation must repeat
the same authorization checks so a cached catalog cannot preserve revoked access.
Responses should identify each tool's source server, required permission and
availability without exposing tools the caller cannot use.

MCP calls should produce scoped audit records with actor/credential, project or
global scope, server/tool, outcome, stable error category and duration. Do not
record arguments, results, secrets or upstream response bodies. Add configurable
policies for sensitive write tools, with explicit approval where required and
revalidation of identity, grants and target resources when approval is applied.

The authorization model already distinguishes global grants from instance
grants: global `resource.read` covers global resources, while project search and
project data remain limited to projects the caller can read. Add a separate
global `project.discover` permission for bounded project-directory search that
returns project metadata only; it must not grant project content access. Project
creation remains instance-scoped `project.create`; it does not grant access to
every project.
For MCP/API-key creation, the plan is to atomically give the creating
human-bound credential `resource.read` and `resource.write` on only the project
it created. This narrow derived grant must be audited, remain subject to live
membership, and never imply project management, execution, MCP administration,
or access to future projects. Failed project creation must leave no grant.

Acceptance requires parity between HTTP and stdio discovery/calls; immediate
effect of grant revocation, server disablement and read-only changes; no
cross-project/global leakage in search or audit; and transactional tests for
project creation, scoped grant derivation and failure rollback. These are
planned requirements, not behavior in the current 0.3.11 candidate.
