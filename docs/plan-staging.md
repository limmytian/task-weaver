# Plan staging

A project member with write access can save a plan draft, edit it and review the resulting impact before explicitly applying it. Drafting does not create requirements, tasks or execution slices. Existing entities in a plan are references; their fields are not updated by the draft. A new staged requirement starts in `draft` and a new staged task in `todo`; approving the requirement is a separate action. Adding tasks or dependencies to an existing requirement can affect its execution and is subject to its lease and planning-change controls.

Open **Plans** on a project page to create or reopen a draft, or use **Plan work for this requirement** on a requirement page to start with a reference to that requirement. The editor provides a dependency graph, slice lanes and keyboard-accessible list controls for tasks, slices and dependencies. Save before validating. The review shows create/reuse counts, workflow sources, dependencies, slice order and warnings. Apply only after reviewing those effects. A successful application has a durable receipt; reopen the draft URL to view it. If a draft or project changes after validation, validate again. A conflicting save keeps the current browser edits; copy or reconcile them before opening the newer revision.

REST endpoints under `/api/v1/plans/drafts` provide create, project-scoped list, get, update, discard, validate, apply and receipt operations. Update and discard require the expected draft revision. Apply requires the validated revision and an operation UUID; retry the same draft and operation UUID to retrieve the same receipt. Reusing a key for another draft conflicts. Each operation checks current authorization. MCP clients can use the explicit `tw_plan_stage` tool to obtain a draft ID and Web path; the existing direct plan tools retain their separate semantics.

Staged plans are limited to 1 MiB after normalization, 100 requirements, 100 documents, 200 tasks, 500 dependency edges and 20 slices. Oversized REST and Web requests are rejected before JSON parsing. Drafts expire 30 days after creation; expired drafts cannot be read, edited or applied. Creating a draft opportunistically removes up to 100 expired draft or discarded records in that project; applied records and receipts remain available to support replay. Projects without subsequent draft creation require operator-managed cleanup. The schema migration is additive and does not alter existing plans or business entities.
